## 三、需求拆解（面试「给你个模糊需求怎么拆」直接套）

| 环节     | 内容                                                                        |
| ------ | ------------------------------------------------------------------------- |
| **场景** | 应届生在 BOSS 上一天刷 30 个岗位，每投一个都要判断「我配不配、该不该投」                                 |
| **痛点** | 判断全靠感觉。要么觉得「差不多能投」结果石沉大海，要么自我否定错过能拿的岗。真正的痛苦不是被拒，是**不知道自己差在哪一条**           |
| **方案** | 用 LLM 做结构化诊断：4 维加权评分 + 每条结论必须引用 JD 与简历原文 + 给出可直接替换的改写句 + 3 条 7 天行动        |
| **指标** | 核心：诊断结论被采纳率（看完愿意按建议改简历并投递）<br />护栏：编造率（≤10%）、证据可追溯率（≥90%）、单次耗时（P95 ≤ 45s） |

**为什么不用「AI 一键改简历」做切入？**  
因为一键改简历是「给答案」，用户不知道答案为什么对；诊断是「给判断」，用户能学会自己判断。前者用完就走，后者会复用。而且一键改简历的失败模式是灾难性的——改完投出去被拒，用户会怪产品；诊断即使不准，用户也会自己复核。

## 五、PRD 骨架（3-5 页，按这个结构写）

```
1. 背景与问题
   1.1 用户是谁（应届生 / 转岗者）
   1.2 现状与痛点（要写具体数字：一天刷几个岗、多久判断一次）
   1.3 为什么现在做（LLM 让结构化诊断成为可能；以前只能靠人）

2. 目标与不做什么
   2.1 目标：让用户在 1 分钟内判断"该不该投、差在哪"
   2.2 非目标：不做简历自动生成、不做岗位推荐、不做投递托管
   ← 这一条最容易漏，但面试官特别爱问"边界在哪"

3. 用户故事
   - 作为应届生，我想知道这条 JD 我到底差哪一条，以便决定要不要投
   - 作为转岗者，我想知道我的旧经验能迁移多少，以便决定怎么讲

4. 核心流程
   输入 → 校验 → 诊断生成（流式）→ 结果分层展示（结论/证据/改写/行动/风险）→ 落库

5. 异常分支（重点写，这是 PM 和产品助理的分水岭）
   - JD 太短 / 简历太短 → 阻断并提示
   - 简历信息严重不足 → 输出"无法判断"，不给假分数
   - 模型输出不是合法 JSON → 降级展示原始文本并提示重试
   - 流式中断 → 保留已生成内容 + 重新生成按钮
   - 额度耗尽 / 模型不可用 → 明确错误文案，不静默失败
   - 用户粘贴含隐私信息 → 提示不要粘贴身份证/手机号

6. 验收指标
   - 功能：12 条评测集中 v3 通过率 ≥ 75%
   - 质量：编造率 ≤ 10%，证据可追溯率 ≥ 90%
   - 性能：P95 生成耗时 ≤ 45s
   - 体验：3 位测试用户中 ≥ 2 位表示"愿意照着改简历"

7. 上线计划
   - MVP：单用户本地可用 → 加登录与记录 → 加评测集 → 找 10 人试用
```

## 六、竞品分析怎么做（选 3 个即可）

建议对标：**BOSS 直聘的「简历优化」**、**超级简历 / 职徒简历的 AI 诊断**、**通用大模型（豆包/Kimi）直接问**。

| 维度       | 你的产品          | 通用大模型直接问 | 简历工具内置 AI | 招聘平台内置 |
| -------- | ------------- | -------- | --------- | ------ |
| 定位       | 单次求职决策支持      | 万能助手     | 简历制作提效    | 平台内转化  |
| 输出是否可追溯  | ✅ 逐条引用原文      | ❌ 一段建议   | ⚠️ 部分     | ❌      |
| 是否给分数    | ✅ 4 维 + 权重    | ⚠️ 随口给   | ⚠️ 单一总分   | ❌      |
| 是否有评测体系  | ✅ 12 条 + 5 指标 | ❌        | ❌         | 未知     |
| 是否积累个人数据 | ✅ 记录落库        | ⚠️ 对话历史  | ✅         | ✅      |
| 商业化      | 暂无            | 订阅       | 会员        | 招聘佣金   |

**你的差异化一句话**：别人给的是"建议"，你给的是"可核对的证据链"。用户不信 AI 的建议，但会信"JD 要 X，你简历里写的是 Y"这种对照。

**你的劣势（主动说出来）**：没有真实用户规模，没有品牌，冷启动完全依赖内容传播。

## 七、必须真做的一件事：用户验证

模板（拿去问人）：

> 我做了个工具，能判断你的简历和某个 JD 差在哪，2 分钟。帮我试一下？  
> 试完想问三件事：
>
> 1. 这个分数你觉得准吗？哪部分最不准？
> 2. 给你的改写建议，你会照着改吗？为什么？
> 3. 有没有哪个瞬间你想直接关掉？

把回答原话记下来，一条都别美化。**面试官问「用户有什么反馈」，你能说出原话，比说「反馈很好」强十倍。**

另外：**第 3 个问题（想关掉页面）的回答，就是你的下一个迭代点**。这就是产品感。

## 八、面试要怎么讲（90 秒版）

> 我在准备 AI 产品岗的时候发现一个问题：市面上所有 AI 简历工具都在「帮你改」，但没人告诉你「为什么该这么改」。而求职者真正需要的是判断，不是代笔。
>
> 所以我做了一个 JD 匹配诊断器。核心设计是逼模型不许编：我把每条 JD 要求对应到简历原文，标成命中、缺失、或者存疑；声称命中就必须逐字摘出简历原话。改完之后我没说「更好了」，而是建了 12 条评测集——里面有跨行迁移的、有过度包装的、有故意写成空白的——用同一套规则算出编造率从多少降到多少、证据可追溯率从多少升到多少。
>
> 这个过程让我真正理解了一件事：AI 产品的护城河不在模型，在约束层和评测层。模型是公共的，真正决定产品好坏的是你怎么约束它、怎么证明它变好了。

**追问预案**：

- 「你这个评测指标怎么定的？」→ 4 项指标全部是规则可算的，不用模型自评，否则就是拿感觉证明感觉
- 「12 条样本够吗？」→ 不够，只能发现明显退化，做不了显著性检验。下一步要扩到 100 条并做人工双标
- 「为什么不做成小程序？」→ 简历和 JD 是长文本，手机端粘贴体验差；这是个「坐下来认真准备」的场景，不是碎片场景
- 「用户从哪来？」→ 诚实答：还没解决。我目前的假设是从小红书「简历诊断」类内容切入，但我没有验证过
- 「你觉得这个产品会死在哪？」→ 死于「诊断完用户不知道下一步」。所以我把「7 天行动」做成硬性输出，但这一块还没有数据验证

## 九、这个项目的已知局限（主动说，别等被问）

1. **无法验证经历真伪**：只能判断「简历里有没有证据」，判断不了「经历是不是真的」
2. **分数不是绝对值**：65 分不是「你这个人 65 分」，是「在这条 JD 口径下证据覆盖度是 65」
3. **评测集只有 12 条**：样本小，只能发现明显退化
4. **未做真实用户规模验证**：这是最需要补的一块，也是你 Day 3 要做的
5. **模型相关性**：同一 Prompt 换模型效果会有波动，目前只测过一个模型

## 十、下一步：项目 02 和 03 做什么

按你资料库的 JD 权重，这个项目补完「Prompt + 评测 + PRD + 数据」之后，还缺两块：

| 缺口            | 对应 JD 提及率 | 项目 02 建议                                                       |
| ------------- | --------- | -------------------------------------------------------------- |
| Agent / 工作流编排 | 37.8%     | **「面试模拟 Agent」**：多轮对话 + 工具调用（查岗位库、查简历、生成追问）+ 人工兜底，重点做「任务完成率」评测 |
| 用户运营 / 增长     | 16.2%     | **「AI 工具冷启动作战」**：不写代码，做 1 次真实的小红书内容投放，记录曝光→点击→试用→反馈的漏斗，出一份复盘   |

**优先级：先做 Agent，再做运营。** 因为 Agent 方向的岗位 JD 更多、且技术门槛能帮你把「只会写文档」的候选人都筛掉。
