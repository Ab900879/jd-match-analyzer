# 语音面试官（Voice Interviewer）

> 一个练面试的小工具：它念题，你回答，它判断你说得够不够，不够就追问。
> 结构跟企业的语音 Agent 是同一套：**听（ASR）→ 判（规则+模型）→ 说（TTS）**。

---

## 一句话

**面试没法自己练。** 对着镜子不知道答得够不够，找人模拟人家没空，用文字和 AI 聊又不是"张嘴说"的感觉。
这个小工具专门解决这件事：逼你真的把话说出来。

---

## 它怎么工作

```
题库 questions.json
      │
      ├──→ TTS 念题（edge-tts，生成 mp3 缓存）
      │
      ├──→ 你回答（麦克风 → waveIn 录音 → 剪静音 → 转写成文字）
      │
      ├──→ 规则判断：够不够？
      │       ├── too_short      说得太短
      │       ├── no_concrete    全是空话，没有具体的事
      │       └── missing_keywords 没说到这题的关键点
      │
      ├──→ 没过 → 追问一句（模型润色；没 key 就用规则模板）
      │
      └──→ 记录 logs/sessions.jsonl → 之后按规则统计 badcase
```

---

## 运行

```bash
pip install edge-tts openai        # 这两个是必须的
pip install faster-whisper         # 想用本地转写就装（首次会下模型，约 500MB）

python main.py --devices        # 先看有没有能录音的麦克风
python main.py --listen-only    # 只念题，确认声音正常
python main.py                  # 文字模式：它念题，你打字回答
python main.py --voice          # 完整模式：它念题，你说话
python main.py --report         # 看积累下来的 badcase 分布
```

配置模型（可选，不配就用规则版追问）：

```bash
setx DEEPSEEK_API_KEY "sk-你的key"
```

想用在线转写而不是本地 whisper，另外设两个变量（任何 OpenAI 兼容接口都行）：

```bash
setx STT_API_BASE "https://api.siliconflow.cn/v1"
setx STT_API_KEY  "sk-你的key"
setx STT_MODEL    "FunAudioLLM/SenseVoiceSmall"
```

## 它准不准：实测数据

判断规则不是写出来就算完的东西，得拿真实口吻的回答去撞。
所以除了 14 条回归集，还留了 14 批**盲测**——每批写完直接跑，跑完记数字，不许回头改。

### 怎么读这张表

- **回归集**（`test_judge.py`，14 条）：我改规则后确认"没弄坏什么"。它被看过、调过，通过率只能说明稳定，不能说明准。
- **盲测**（`test_blind.py`，95 条 / 8 批）：独立写的，跑完才看结果。**被调过的批次就不再是盲测**，所以每批单独记，不合并成一个好看的总数。

| 批次 | 条数 | 结果 | 说明 |
|---|---:|---:|---|
| 第 1 批 | 8 | 8/8 | 调过 |
| 第 2 批 | 12 | 12/12 | 调过 |
| 第 3 批 | 8 | 8/8 | 调过 |
| 第 4 批 | 7 | 7/7 | 调过 |
| **第 5 批** | 12 | **10/12** | **终验，未调过** |
| **第 6 批** | 12 | **12/12** | **终验，未调过** |
| **第 7 批** | 6 | **6/6** | **终验，未调过** |
| **第 8 批** | 9 | **9/9** | **终验，未调过** |
| **第 14 批** | 21 | **18/21** | **终验，未调过** |
| 合计（去重后固化在 test_blind.py） | 95 | **90/95（94.7%）** | |

第 9～13 批（26 + 24 + 25 + 30 + 25 = 130 条）是调参过程中跑掉的，参与过规则修改，
它们只用来定位问题，不列入"准确率"——否则就是在用训练集报成绩。

### 最后那 5 条错在哪（不是漏修，是修不到）

这 5 条全部集中在**三类结构性缺口**上。写在这里，是因为知道边界比知道分数重要：

| 缺口 | 例子 | 为什么这套判据做不到 |
|---|---|---|
| **取向型动机** | "我不太喜欢做那种做完就扔的东西。做 AI 产品能看到它被人天天用，被骂也好，这个反馈对我很重要。" | 它表达的是**价值取向**，不是经历。锚点体系里有数字、专名、动作、因果、类比五类，没有"取向"这一类 |
| **平行对仗** | "通信做的是把信号从这头传到那头，我觉得 AI 产品做的是把意思从人这头传到那头，是一类问题。" | 语义上是最漂亮的类比，但字面没有"像/一样/一回事/同理"任何一个词。正则抓的是词，抓不到**结构对仗** |
| **时间维度提议** | "现在质检报告出来得太慢，隔天才看得到，我想改成当天就出。" | 讲清了"哪里不好+改成什么"，但两组要点词都没命中（缺"电话/外呼/坐席"，"隔天/当天"不在词表）。正确判法是"时间维度上的改动"，跟词表无关 |

**这三条要想真解决，只有一条路：上语义判断（小模型或 embedding），
而不是继续加词。** 加词能到 95%，但那是过拟合，第 15 批就会掉回去。
现在的做法是：把边界写清楚，让它可预期——知道它在什么情况下判不准，比一个虚高的准确率有用。

## 设计取舍（这部分是这个项目真正值钱的地方）


### 1. 为什么"该不该追问"用规则，不用模型

模型判断不稳定：同一句回答，今天追问明天不追问。而你练面试需要**可预测**——不然你不知道是自己答得差，还是它心情不好。

所以拆开：**规则决定"要不要追"和"往哪追"，模型只负责把追问那句话说得自然。**

好处是出了问题能定位：追问错了，看是哪条规则误触发，改规则就行。

### 2. 规则踩过的坑（真实的两次返工）

**第一次误判**：`must_mention` 写的是 `["我","做","项目"]`，一句完全正确的回答因为没用"项目"这个词，被判"漏要点"。
→ 改成**关键词组**，组内任一命中即可。

**第二次误判**：q2 问"最头疼的问题"，一句很具体的回答（描述的是"分数很低""判它漏了"这种**现象**）没有出现"问题"两个字，又被判失败。
→ 词表从"概念词"改成**"现象词"**：把 `错、不对、失败、分数低、崩、漏` 这些都加进去。

**这两次说明一件事**：文字匹配的规则天生不稳，它不知道"什么算说到"，只知道"有没有那几个字"。
— 这跟我另一个项目里踩的坑是同一个：**评测工具判错了一条好答案，问题不在模型，在尺子。**

### 3. 为什么题库要分那么多列

每道题除了题干，还写了 `focus`（考什么）、`pass_criteria`（答成什么样算过）、`must_mention`（关键点）、`followup`（答不好往哪追）。

只写题干的话，第二期就没法判断——**判断需要有标准，标准得写在数据里，不能写在脑子里。**

### 4. 语音为什么要提前生成、存成文件

练的时候每道题都等几秒生成很烦。所以第一次跑时一次性全生成，存到 `audio/`，之后直接播本地文件。
代价：改了题目文字要删掉对应 mp3 才会重新生成。

### 5. 为什么默认是文字模式

语音链路长（麦克风→录音→转写），一上来全上，出错不知道哪一段坏的。
先用文字把"判断+追问"跑对，再接麦克风。**这就是分期的意义，不是功能残缺。**

### 6. 录音为什么最后用 waveIn，而不是网上抄来的 mci 写法

这是本项目返工最多的一块，值得说清楚。

第一版用 `mciSendString`，写法是从教程上抄的：

```python
mci('open new type waveaudio alias vi_rec')
mci('set vi_rec channels 1 samplespersec 16000 bitspersample 16')
mci('record vi_rec')
...
mci(f'save vi_rec "{out}"')
```

**结果录出来一个 44 字节的文件——只有 WAV 头，时长 0.0 秒。**

排查过程（这部分是真正学东西的地方）：

1. 先怀疑路径。`save` 传的是相对路径，而 Python 的 cwd 和进程初始目录不一定一致 → 改成 `out.resolve()` 绝对路径。**没解决。**
2. 再怀疑 alias 没关。没 `close` 的话下次 `open` 拿不到设备 → 包成 `_Recorder` 类，`finally` 里强制 close。**还是 0 字节。**
3. 加上错误码翻译（`mciGetErrorStringW`），让 `open`/`record`/`save` 每步都报真实错误。**真相出现了：**

   ```
   录音失败（开始录音）：未安装可按当前格式记录文件的波形设备。
   ```

   也就是说 `open` 一直返回成功，但它只是建了个**空对象**——根本没绑定到任何录音端点。
   而 `record` 拿不到设备，就静默出了个 0 时长文件。

4. 换 `waveIn` 系列 API（`waveInOpen` / `waveInPrepareHeader` / `waveInStart`）。
   每一步都有明确返回码，`waveInGetErrorTextW` 能说出"设备被占用"还是"没有驱动"。
   同时用 `waveInGetNumDevs` + `waveInGetDevCapsW` 枚举设备——这才是**真实可录音的端点**。

对比一下两边的设备清单：

| 查法 | 结果 |
|---|---|
| 一开始用 `Get-PnpDevice -Class AudioEndpoint` | 9 个：NVIDIA Virtual Audio、Nahimic mirroring、Steam Streaming… 全是虚拟驱动/输出设备 |
| 换成 `waveInGetNumDevs` | **1 个**：`麦克风阵列 (Realtek(R) Audio)` |

**这一步的教训**：`open` 返回成功，不等于真的打开了设备。链路上只要有一步"成功得没有意义"，后面全是假象。所以宁可多写二十行，也要让每步都能报出真实原因。

顺带一个坑：`subprocess.run(..., text=True)` 读 PowerShell 输出时，中文 Windows 默认是 GBK，按 utf-8 解会抛 `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd1`。要手动 decode 并按 `utf-8 → gbk → mbcs` 逐个试。

### 7. 转写为什么做成可替换的，而不是绑死 whisper

`faster-whisper` 要下 500MB 模型，客户环境里不一定让你下；企业采购的 ASR 也往往已经定了（讯飞、阿里云、火山）。
所以 `voice_io.py` 里定义了 `Transcriber` 基类，两个实现：`LocalWhisper`、`OpenAICompatTranscriber`，靠环境变量切。

**关键是没有"装不上就退回打字"这条降级路。**
第一版写了这个降级，看起来贴心，实际上是害人：用户以为在练语音，其实还在敲键盘，面试时照样张不开嘴。
现在的做法是——录不上就报录不上的原因，转写不了就报转写不了的原因，**但不会假装成功。**

这就是"可替换"和"降级"的区别：前者换方案但目标不变，后者偷偷把目标降低了。

## 判据是怎么长出来的（这一段最值得看）

第一版我把它当成"找关键词"，结果每换一种说法就失效。
后来发现真正的分界线不是"词多词少"，而是**判的是字面还是结构**：

| 层 | 判什么 | 手段 | 例子 |
|---|---|---|---|
| **锚点判据** | 说的东西是否具体、可复述 | 结构 | 数字（"压到百分之三"）、专有名词（"ASR""whisper"）、动作+对象（"加了个队列"） |
| **意图判据** | 有没有答到这道题 | 关键词分组 | q3 要"标准"或"比例"，q2 要"问题"和"改法" |
| **门槛判据** | 有没有展开 | 字数 | q6 反问 20 字够，q1 讲项目 20 字肯定不够 |

**顺带一条更重要的纪律：词表是补丁，结构才是根因。**

盲测里每抓到一个错，我有两种修法：
- 补词表（快，但下次换说法又漏）
- 找同类错误的**根因**，按类别修（慢，但一次修一批）

举个例子。有一批同时错了三条：
"做过一个语音识别的课设"、"按逗号切不行"、"缓存没清"。
补三个词能修好这三条，但第四批还会在"做过一个 XX 的 YY"上再栽一次。
根因是：**`动词+量词+名词` 这个兜底句式会放过泛指名词**——
"一个课设""一个东西""一个想法"结构上跟"一个告警"长得一样，信息量却为零。
所以改成按**中心词**判（中文定语都在前面，尾巴才是落点），一次修掉一整类。

### 判据踩过的具体坑（都留了注释在代码里）

- **中文数词**：第一版 `[一二三…]{1,4}(?=量词)` 把"三千多"拆成"一/千/一"，于是任何带"一"的句子都算有数字；改完"第一次"又成了数字（序数是序数，不是量级）
- **"半小时"** 不在数词表里，一句"原来人工填半小时，现在点一下就出来"被判没有数字
- **宾语在动词前面**："把投诉过的号码过滤掉"——中文最标准的处置式，只看动词右侧的窗口，这类句子一条都过不了
- **动词被包在名词里**："对好的**定**义不太一样"里的"定"、"一**个统一**的标准"里的"统一"，都被当成了动作
- **否定后缀**："测的时候一直**通不过**"——动作没成，不能算"我做过什么"
- **"不一样"里有"一样"**："to B 和 to C 标准完全不一样"被类比规则命中，方向正好反了
- **趋势句最容易混过去**："因为 AI 是未来方向，我很看好这个行业"——凑得出"看好+方向"，但一件真事都没有
- **通道开在错的层里**：动机题的"自我认知"通道一开始写在 `rule_missing_keywords` 里，结果这些回答在 `rule_no_concrete` 就被拦掉了，根本走不到那一步。**规则有顺序，通道开在后面等于没开**

## 已知局限（写在前面）

- 判断只有三条规则，很粗；"说得空"这件事本质需要语义判断，字面规则只能兜住最明显的情况
- **判据的硬上限在 95% 上下**：取向型动机、平行对仗、时间维度提议这三类结构性表达抓不到（见上面「最后那 5 条错在哪」）。再往上必须换语义判断，加词只会过拟合
- **通话级语音链路没做**：没有实时 VAD、没有全双工打断、没有流式转写。现在是"录固定时长→录完再转写"，延迟 3~5 秒。真做电话机器人这些是必须的（见"下一步"）
- 录音是**固定时长**，说到一半没话了也要等它录完（有尾部静音剪裁，但前半段空等省不掉）
- 转写准确率取决于用哪个模型；本地 small 模型对口音重的会错
- 追问只追一次，真实面试可能连环追问
- 没有录音回放，练完听不到自己怎么说的
- 没有和岗位 JD 挂钩，题库是通用的 AI 产品实习面试
