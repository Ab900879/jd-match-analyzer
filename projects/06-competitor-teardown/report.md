# 盲评实验报告：把一次手工对比升级成可复现的评测

> 2026-11-03 · 被测 kimi-k2.5 / glm-5.3-flash / deepseek-v4-flash · 评分 minimax-m3.1-flash · 105 次真实调用
> 数据文件：[`lab/lab-data.json`](lab/lab-data.json)（30 份答案 + 60 条评分，原始未美化）

---

## 一、为什么要做这次实验

原始评测（2026.06-07，豆包 / 通义 / Kimi 三款 App，90 次手工测试）有一个方法论漏洞：**明评**。
我知道每份答案来自哪个产品，打分时品牌印象会不自觉地加进去——这个偏差可以大到盖过产品之间的真实差距。

本次实验的目的不是重新排名三款 App，而是**把评测协议本身升级并验证它可自动化执行**：

| 升级点 | 原来 | 现在 |
|---|---|---|
| 任务集 | 在我脑子里和截图里 | [30 题开源](tasks.json)，题目全部具体化 |
| 评分 | 明评（知道品牌） | 盲评（打乱 + 匿名 + 评分模型与被测不同厂商） |
| 硬约束 | 人眼数 | 代码判（字数 / 必含数字 / 条数 / 禁用词） |
| 信度 | 没有 | 同一批答案二评，算一致率 |
| 结论 | 一张对比表 | 一张对比表 + 一致率 + 冲突仲裁清单 |

## 二、实验设计

- **被测（三家不同厂商）**：kimi-k2.5（月之暗面）、glm-5.3-flash（智谱）、deepseek-v4-flash（DeepSeek）
- **评分（第四家厂商）**：minimax-m3.1-flash——与被测全部不同，避免"给自己加分"
- **题目**：W01-W05（写作）+ S01-S05（总结）。联网题 N01-N10 无法在 API 模型上测，留给消费级 App 的正式评测
- **流程**：生成（temperature 0.3）→ 固定种子打乱（seed=20261103，可复盘）→ 匿名盲评（0-2 分）→ 机器判硬约束 → 二评 → 解盲汇总
- **完整协议**：[protocol.md](protocol.md)

### 信度（二评一致率）

- 完全一致：**24/30 = 80%**

按 protocol.md 自己定的标准，80% 落在 70%-85% 区间 → **本报告结论标注"仅供参考"，6 条不一致条目需人工复核后才能定稿**。协议的降级条款第一次被自己触发。

## 四、发现

**1. 质量层差距不大，真正拉开的是指令遵守和速度。**
盲评均分三家挤在 1.4-1.7，但 deepseek 硬约束过 9/10、平均 1.9 秒；kimi 硬约束 7/10、4.0 秒。"哪家模型好"是个错误问题，正确问题是"什么任务用哪家"——和原始评测"按任务选工具"的结论一致，但现在有数据了。

**2. 三层判定各抓各的，缺一层都会漏。**
机器判和盲评冲突的 3 条，正好每层抓到别的层抓不到的东西：

| 条目 | 机器判 | 盲评 | 谁对 |
|---|---|---|---|
| 答-019（kimi·W01） | 过（字数结构全合格） | **0 分：编造**"监控数据""占用1人日"原文里没有 | 盲评对。机器判不了"编造" |
| 答-014（deepseek·W04） | **超字数**（第2条含风格标注 19>18） | 2 分 | 灰色地带：标注算不算字数，只能人来定 |
| 答-027（glm·W04） | 条数不符（把样式标签行数成了标题） | 2 分 | 盲评对。我的判定器误报 |

这 3 条就是"人工仲裁层"存在的全部理由——不是流程装饰，是真的会撞上。

**3. kimi 的写作弱项有具体证据。**
W01 得 0 分的唯一原因不是文笔，是**补细节**：把"上线了一个小功能"写成"上线XX小功能并监控数据"、凭空加了"占用1人日"。总结类它不弱（S01/S02/S04 全 2 分）。这个模式（总结保真、写作添油加醋）在 10 题里稳定出现。

**4. 评分器自己的三个 bug（都在本实验中被抓出来修掉）：**

| Bug | 现象 | 修法 |
|---|---|---|
| 字数统计把 markdown 的 `**` `#` 数进去 | 用 markdown 排版的答案被冤枉超字数 | 计数前剥掉修饰符，离线重算（零调用） |
| 评分输出 maxTokens=400 截断 | 60 次评分 15% 解析失败 | 提到 1200 + 解析重试，补评后 0 失败 |
| 标题计数把样式标签行当标题 | 条数误报 | 保留为已知误报边界，写进仲裁清单 |

第三条没修——它是个真边界（机器分不清"标签行"和"标题行"），修成特判反而藏问题。**修判定器和修模型是同一件事：先修尺子，再谈分数。**

## 五、局限

- **API 模型 ≠ 消费级 App**：本实验验证的是协议可自动化，豆包 / 通义 / Kimi 三款 App 的正式评测仍需按 [protocol.md](protocol.md) 人工采集（App 有登录墙）。
- **10 题 × 3 模型**只够看方向，不做统计显著性声明。
- LLM 评分器对长回答、结构化排版有偏好；缓解手段是硬约束归代码、冲突归人工，但偏差不可能归零。

## 六、怎么复现

```bash
node lab/run.mjs all        # 全流程：生成→盲评→二评→汇总（约 8 分钟，105 次调用）
node lab/run.mjs remachine  # 判定器改完后离线重算机器判（零调用）
```

被测模型、评分模型、打乱种子都写在 `lab/run.mjs` 顶部，换模型改三行即可。
