# 06 · 主流 AI 产品对比拆解（豆包 / 通义 / Kimi）

> 一句话：三个产品、同一套题、90 次测试，结论是什么任务用哪个。后来发现这个评测本身有个漏洞（明评），把它升级成了可复现的盲评协议，并用三家模型端到端验证过。

## 两个版本

| | v1（2026.06-07） | v2（2026.11） |
|---|---|---|
| 形式 | 手工测试三款 App，90 次 | 任务集 + 盲评协议 + 自动化实测 |
| 评分 | 明评（知道品牌） | 盲评（打乱 + 匿名 + 评分模型与被测不同厂商） |
| 开源 | 只有设计（截图含账号，未放） | [30 题任务集](tasks.json) + [协议](protocol.md) + [实验数据](lab/lab-data.json) + [报告](report.md) |

## v1 · 评测设计（仍然有效）

**3 个产品 × 3 类场景 × 每场景 10 个任务 = 90 次测试**，全部同一时段完成，控制模型版本波动。

| 场景 | 任务示例（每个场景 10 个） | 考察点 |
|---|---|---|
| 写作 | 周报润色、小红书文案、邮件改写、标题生成… | 语气控制、格式遵循、字数遵守 |
| 总结 | 万字长文摘要、会议记录提炼、多轮聊天归纳… | 信息保真、结构化、不遗漏关键数字 |
| 联网搜索 | 查最近发布的产品、核对某政策原文、找数据来源… | 时效性、来源标注、幻觉率 |

评分口径（每任务 0-2 分）：**2** = 可直接用；**1** = 可用但需手动修正；**0** = 不可用 / 编造关键信息 / 拒绝执行。

三条关键口径决策：

1. **同一个提示词喂三个产品**，不为每个产品单独优化——测的是默认能力，不是调参能力。
2. **联网类任务当天完成**——时效衰减会让隔周补测失效。
3. **幻觉单独计**：编造来源链接的联网回答，直接 0 分。

结论框架：**按任务选工具，不存在全能冠军**。如果一家在所有任务上都赢，多半是我的维度设计有问题。

## v2 · 盲评协议（本次加深）

v1 的漏洞：我知道每份答案来自哪个产品再打分，品牌偏差可能盖过真实差距。[protocol.md](protocol.md) 用六步流程消掉它：

```
采集 → 脱敏 → 打乱（固定种子）→ 盲评 → 二评 → 解盲汇总
```

三层判定，各司其职：**硬约束（字数/必含数字/条数）代码判，质量盲评由第四家厂商的模型判，两层打架的归人工仲裁。**

### 自动化实测（105 次真实调用）

被测 kimi-k2.5 / glm-5.3-flash / deepseek-v4-flash（三家厂商），评分 minimax-m3.1-flash（第四家），10 题盲评 + 二评：

| 模型 | 盲评均分 | 可用率 | 硬约束 | 速度 |
|---|:--:|:--:|:--:|:--:|
| kimi-k2.5 | 1.40 | 9/10 | 7/10 | 4.0s |
| glm-5.3-flash | 1.50 | 9/10 | 7/10 | 3.3s |
| deepseek-v4-flash | 1.70 | 10/10 | 9/10 | 1.9s |

三个值得看的发现（完整归因在 [report.md](report.md)）：

- **质量差距不大（1.4-1.7），拉开差距的是指令遵守和速度**——"哪家好"是错的问题，"什么任务用哪家"才是对的。
- **三层判定缺一层都会漏**：机器判抓字数、盲评抓编造（kimi 周报凭空加"占用1人日"被盲评抓到，机器判不了编造）、机器判自己也会误报（把样式标签行数成标题）。
- **二评一致率 80%，正好触发协议自己的降级条款**（70-85% → 结论标"仅供参考"）。尺子先于分数。

### 复现

```bash
node lab/run.mjs all        # 全流程约 8 分钟
node lab/run.mjs remachine  # 改判定器后离线重算（零调用）
```

## 还没做的（和为什么）

- **三款消费级 App 的正式盲评没跑**：App 有登录墙，无法脚本化；需要按 protocol.md 人工采集（同题同提示词 → 截图脱敏 → 打乱 → 隔天盲评）。协议已就绪，等采集。
- **联网题（N01-N10）在 API 模型上测不了**：API 不带 App 的搜索功能，混测会不公平。

> 评测设计迁移：这套「场景 × 任务 × 0-2 分口径」后来演化成了项目 01 的 12 条分层评测集、项目 03 的 4 条打分规则，以及项目 02 的判定器教训（先修尺子，再谈分数）。
