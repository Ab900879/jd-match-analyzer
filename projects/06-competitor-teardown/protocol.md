# 盲评协议 v2

> 为什么要有这份协议：原始评测（2026.06-07）是**明评**——我知道每份答案来自豆包、通义还是 Kimi。
> 知道品牌再打分，会不自觉地给熟悉的产品加分、对失望的产品苛刻。这在评测方法论里叫**评分者偏差**，
> 它能大到盖过产品之间的真实差距。v2 用盲评把它消掉。

## 一、流程（六步）

```
采集 → 脱敏 → 打乱 → 盲评 → 二评 → 解盲汇总
```

| 步骤 | 做什么 | 关键约束 |
|---|---|---|
| 1 采集 | 同一道题、同一个提示词、同一时段发给所有产品 | 联网题（N01-N10）**当天全部完成**，隔周补测会让对比失效 |
| 2 脱敏 | 去掉答案里的产品标识、水印、界面痕迹；统一纯文本格式 | 保留原文，只去身份信息 |
| 3 打乱 | 所有答案随机编号（答-001、答-002…），编号与产品的对应关系单独存一份，评测期间不可见 | 打乱顺序固定记录，保证可复盘 |
| 4 盲评 | 评测者只看到「题目 + 匿名答案」，按 0-2 口径打分 | 评测者不知道任何一份答案来自哪个产品 |
| 5 二评 | 间隔 ≥24 小时，对同一批答案重新打分 | 算两次的一致率（见第三节） |
| 6 解盲汇总 | 打分全部完成后才把编号换回产品名，出对比表 | 顺序不可颠倒 |

## 二、三层判定（不是全靠人打分）

| 层 | 判什么 | 谁判 | 为什么 |
|---|---|---|---|
| 硬约束 | 字数上限、必含信息（价格/时间/数字）、禁用词、条目数 | **代码判**（`lab/run.mjs` 里的 machine 检查） | 客观、零成本、可复现，模型和人都会数错字数 |
| 质量 | 语气、结构、归纳准确度、可用性 | **模型盲评**（评分模型与被测模型不同厂商） | 主观维度需要判断力，但必须盲 |
| 仲裁 | 两层冲突、或二评不一致的条目 | **人工复核** | 人只看分歧条目，不从头打分 |

## 三、信度：二评一致率

同一批答案打两次分，两次都判同一个分数（或都判"可用/不可用"同一档）的比例：

- **≥ 85%**：评分可信，对比结论可用
- **70% - 85%**：结论标注"仅供参考"，不一致条目全部人工复核
- **< 70%**：评分口径有问题，先修口径再谈产品差距——**变的是尺子，不是产品**

## 四、评分口径（每题 0-2 分，与原评测一致）

- **2 分**：结果可直接用
- **1 分**：可用但需手动修正（如格式、一两处事实错）
- **0 分**：不可用 / 编造关键信息 / 拒绝执行

三条关键口径决策（继承自 v1，仍然有效）：

1. **同一个提示词发给所有产品**，不为任何一家单独优化——测的是默认能力，不是调参能力。
2. **联网类任务当天完成**——时效衰减会让隔周补测无效。
3. **幻觉单独计**：编造来源链接的联网回答，不管多流畅直接 0 分。

## 五、已知局限（诚实清单）

- **LLM 评分器自身有偏差**：对长回答、结构化排版的回答有偏好。缓解：硬约束交给代码，分歧交人工。
- **评分模型必须与被测模型不同厂商**，否则存在"给自己加分"的嫌疑。`lab/run.mjs` 里被测三家（月之暗面 / 智谱 / DeepSeek），评分用的是第四家（MiniMax）。
- **API 模型 ≠ 消费级 App**：lab 演示验证的是**协议本身可自动化执行**；豆包 / 通义 / Kimi 三款 App 的正式评测仍需按本协议人工采集（App 有登录墙，无法脚本化）。
- **样本量**：每场景 10 题，只能看方向性差距，不做统计显著性声明。

## 六、复现

```bash
node lab/run.mjs all    # 生成 → 盲评 → 二评 → 汇总，产出 lab/lab-data.json
```

被测模型、评分模型、打乱种子都写在 `lab/run.mjs` 顶部，改配置即可换模型复跑。
